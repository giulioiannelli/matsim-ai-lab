## Smoke run — persona + comparison tools (qwen3.5, fresh, current build)

Ran `1 qwen3.5 --prompt-variant=persona --num-agents=2 --seed=1
--enable-comparison-tools`. Qdrant started by user; Ollama up; offline-verify
(build + unit tests) green first. 1 eligible agent processed (`25875_1`).

**Result: 0/1 success — `MAX_ITERATION_REACHED`.** 11 rounds, 8 tool calls
(3 comparison), 13.8k reasoning tokens, 7 min. Hit the `maxToolIterations=10`
cap **without ever calling `extract_plan`** → original plan kept.

**Diagnosis (from the round-by-round thinking trace):**
- ✅ **Persona emergence is real.** First-person throughout; repeatedly grounds
  in traits ("I'm a 23-year-old man, I don't have a car") and correctly derives
  the mode constraint (walk/pt only) from "no car/bike".
- ✅ **Tool use is correct.** activity_chain_summary → available_modes(x2) →
  compare_routes(x2) → router_tool(x2); valid args, 0 parse/verify failures,
  no hallucinated tools.
- ✅ **Routing strategy is meaningful.** By round 4-5 it reads compare_routes
  correctly (walk 50 min vs pt 27 min), concludes "pt is much faster, the
  current plan is already good".
- ❌ **It never commits.** Reaches the correct conclusion at round 5, then loops
  — re-calling compare_routes (r6) and router_tool (r8,r9) on facts it already
  has — until the cap. The failure is **convergence/commitment, not reasoning**.

Knife-edge: the Apr-21 run of this same agent succeeded at round 10; this one
looped to round 11. The agent over-deliberates right at the iteration cap.

**Fix levers (next micro-experiment in the realization loop):**
1. Prompt: state that keeping the plan unchanged is a valid outcome that still
   requires `extract_plan`; add a "once you have the facts, commit — don't
   re-query" nudge. (PersonaPromptBuilder / IndividualPrompt.)
2. Raise `maxToolIterations` (10 → ~15) or force `extract_plan` near the cap.
3. Anti-redundancy: discourage re-querying already-known routes.

This is the core finding: with the small model, persona + tool grounding work;
the bottleneck is **getting the agent to stop and commit**.

## Multi-persona fixes + a real latent crash bug (user chose "both together")

Made three edits, then hit and fixed a crash.

**Edits:**
1. `LLMReplanningStrategyModule` selection: probabilistic `if(rand<prob)`
   (random 0/1/2 count) → **deterministic exactly-N, seed-shuffled**. Confirmed:
   now selects 4 *distinct* personas (e.g. 8358_1 = 63yo woman w/car).
2. `RunSiouxFallsLLMAgents`: new `--max-tool-iterations` flag (de-hardcoded 10).
3. `PersonaPromptBuilder`: commit nudge (commit once facts gathered; unchanged is
   valid but still call extract_plan; don't re-query).

**Crash found & fixed (was pre-existing, my selection just surfaced it):**
- Symptom: `IllegalArgumentException: Plan must consist of at least one activity`
  in the iter-1 mobsim → whole run dies (exit 1). Reproducible on seed 1.
- Root cause: `ExtractPlanTool` fallback returns `person.getSelectedPlan()` when
  the LLM's extract_plan args fail to deserialize. In `finishReplanning` that is
  the **same object** as `plan`, so `PopulationUtils.copyFromTo(outPlan, plan)`
  self-copies — copyFromTo clears the destination first → empties the plan → 0
  activities → crash. Old probabilistic selection rarely picked the triggering
  car agent (8358_1), so the bug stayed latent.
- Fix: self-reference guard in `finishReplanning` (`if (outPlan == plan)` → keep
  unchanged, skip copy) + an activity-count guard. Run now completes (exit 0);
  guard logs "is the original (extract_plan fallback); keeping it unchanged".

**Two blockers still open for real multi-persona experiments:**
- **A. Query gating.** Selecting N distinct agents ≠ querying N. Only the selected
  agents that land in the LLM strategy's `planToReplan` that iteration get
  queried (others go to ExpBetaPlanChanger/ReRoute/SubtourModeChoice/…). Result:
  4 selected → only **1 queried** (8358_1). Fix options: query the chatContainer
  (all selected) directly in `finishReplanning`, raise the LLM strategy weight,
  or run more iterations. Architectural — needs a decision.
- **B. Car-plan DTO round-trip.** Car/network-route plans trip the extract_plan
  arg deserialization → fallback → decision not applied (8358_1 success=false,
  extract=false every run). PT/linkId plans work (25875_1 applied fine). So car
  personas currently can't replan. Needs a focused NetworkRouteDTO/ActivityDTO
  deserialization debug. The self-ref guard makes this *safe* (keeps original)
  but doesn't make car replanning *work*.

Net: the crash is gone and reasoning quality is good, but "multiple personas
each successfully applying a decision" is still blocked by A (throughput) and B
(car-plan apply). Both are concrete next tasks.

## Blocker B FIXED — hardcoded activity-type whitelist

Surfaced the swallowed cause by logging in `ExtractPlanTool`'s fallback catch:
`VerificationFailedException: Unknown activity type` (x2). Root cause: `ActivityDTO`
verification checked the activity type against a **hardcoded list**
(home/work/education/shop/leisure/other/errands + interactions) that did NOT
include Sioux Falls' real type **"secondary"**. So every car/everyday persona's
extract_plan failed verification → fallback → (pre-fix) self-copy crash, (post
crash-fix) kept original / never applied. PT personas worked only because their
types happened to be on the list.

Fix: `ActivityDTO.isVerified` now accepts any **non-blank** free-form type (as
MATSim does); removed the hardcoded `isAllowedType` whitelist (dead code) and
the duplicate check. Added `ActivityDTOVerifyTest` (secondary/free-form accepted,
blank/no-location rejected). Also kept the `ExtractPlanTool` fallback-cause
logging (no more silently-swallowed deserialization errors).

**Confirmed end-to-end:** seed-1 run, `8358_1` (63yo woman, car) now
success=true, extract=true, **applied=true**, 7 rounds, 2 comparison-tool calls,
4.8 min. No fallback, no crash, sim completes. First time a car persona finishes
the full loop and applies its decision.

**Only blocker A remains** for multi-persona-per-run: still only 1 of N selected
agents is queried per iteration (planToReplan ∩ chatContainer gating).
